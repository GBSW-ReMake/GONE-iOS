# 문장 다듬기 규칙

> 출처: [toss/technical-writing](https://github.com/toss/technical-writing)의 "Step 3. 문장 다듬기"를 바탕으로 GONE 프로젝트에 맞게 재구성했습니다.
> 원본 라이선스: CC BY-NC-SA 4.0 (Viva Republica, Inc.)

이 문서는 코드 주석과 기획·개발 문서를 작성하거나 리뷰할 때 따르는 기준입니다.

## 적용 범위

- 코드 주석: DocC, 인라인 주석, PR 설명, 커밋 메시지
- 기획·개발 문서: 기능 명세, 워크플로우, ADR, 이슈와 티켓 설명

모든 문서에 원칙 1~5를 적용합니다. 코드 주석에는 원칙 6도 적용합니다.

## 1. 문장의 주체를 분명하게 쓴다

- 개발자가 할 수 있는 행동을 중심으로 씁니다. 도구·기술·시스템을 불필요하게 행동의 주체로 두지 않습니다.
- 도구나 기술의 동작 원리를 설명할 때만 도구나 기술을 주어로 사용할 수 있습니다.
- 수동형 대신 능동형을 씁니다. 예: "설정이 완료되어야 합니다" 대신 "설정을 완료하세요"라고 씁니다.

## 2. 필요한 정보만 남긴다

- 한 문장에는 하나의 생각만 담습니다. 필요하면 문장을 나눕니다.
- "다음으로", "앞서 설명했듯이", "결론적으로", "아시겠지만"처럼 정보가 없는 메타 담화는 제거합니다.
- 같은 의미를 반복하거나 불필요하게 강조하지 않습니다.

## 3. 구체적으로 쓴다

- "설정 수행", "검토 진행" 같은 명사형 대신 동사를 씁니다.
- "가능성이 있다", "일부 경우", "필요할 수도 있다"처럼 모호한 표현을 사용하지 않습니다. 확인된 사실과 조건을 씁니다.
- 누가, 무엇을, 어디에, 어떻게 하는지 생략하지 않습니다.
- "던진다"처럼 실제 동작이 불분명한 은어 대신 "예외를 일으킨다"처럼 동작을 드러내는 표현을 씁니다.
- 성능, 재시도, 제한 시간 등은 구체적인 수치와 기준을 함께 씁니다.
- 변수나 설정값을 다시 언급할 때는 어디에서 정의했고 어디에 쓰는지 맥락을 설명합니다.

## 4. 자연스러운 한국어로 쓴다

- "수행하다", "실시하다", "진행하다"처럼 의미를 더하지 않는 한자어는 제거합니다.
- 영어식 명사형 번역투보다 동사 중심의 자연스러운 문장을 씁니다.

## 5. 용어를 일관되게 쓴다

- 공식 문서의 기술 용어와 대소문자 표기를 따릅니다. 예: Kubernetes, JPA, Flyway, Redis
- 하나의 개념을 여러 표현으로 섞어 쓰지 않습니다.
- 약어는 처음에 전체 이름과 함께 씁니다. 예: SSR(Server-Side Rendering)
- 외래어는 맞춤법보다 업계 관용 표기를 우선합니다. 예: 프론트엔드
- 도메인 용어는 프로젝트 용어집 및 코드 표기와 맞춥니다. 예: `verificationTicket`, `student`, `user`

## 6. 코드 주석에는 이유와 제약을 남긴다

- 코드가 무엇을 하는지 그대로 번역하지 말고, 왜 그렇게 구현했는지 설명합니다.
- TODO와 FIXME에는 담당자 또는 완료 조건을 함께 씁니다.
- 변수명이나 코드만으로 알 수 있는 자명한 내용은 주석으로 남기지 않습니다.
- 예외적인 동작과 제약 조건에는 조건과 수치를 명시합니다.
  - 예: `// Redis 연결에 실패하면 200ms 간격으로 최대 3회 재시도합니다.`

## 적용 방법

1. 코드 주석과 문서를 처음 작성할 때부터 이 규칙을 적용합니다.
2. 문장을 리뷰할 때는 위반한 원칙 번호를 표시하고, 구체적인 교정안을 제안합니다.
3. API 명세, 에러 코드, 락 타임아웃처럼 정확성이 중요한 문서에서는 모호한 표현을 제거하고 수치·조건을 우선해 작성합니다.
4. 프로젝트 내 Notion 에러 코드와 도메인 용어를 기준으로 용어 일관성을 확인합니다.
