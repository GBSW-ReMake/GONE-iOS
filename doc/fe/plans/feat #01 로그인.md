## 1. 목적 및 배경

GONE 사용자가 아이디(또는 전화번호)와 비밀번호로 인증한 뒤 학교 서비스를 이용할 수 있도록 로그인 진입점을 제공합니다.

이번 범위는 **로그인 화면과 인증 요청 흐름**입니다. 스플래시와 회원가입은 로그인 완료·검토 후 각각 별도 계획서, 이슈, 브랜치로 진행합니다.

## 2. 사용자 시나리오

```text
사용자가 앱의 로그인 화면에 진입한다
→ 아이디 또는 전화번호와 비밀번호를 입력한다
→ 입력값이 유효하면 로그인 버튼이 활성화된다
→ 로그인 버튼을 누르면 진행 상태를 확인한다
→ 인증 성공 시 세션을 안전하게 저장하고 다음 화면으로 이동한다
→ 인증 실패 또는 네트워크 오류 시 원인을 안내하고 다시 시도한다
```

## 3. 화면 및 UX

### 화면 구성

- 화면명: 로그인
- 피그마 기준: [로그인 화면 (node 14:1509)](https://www.figma.com/design/l3MKhDJ6ciT7gfSvTpiYNI/%EA%B2%BD%EC%86%8C%EB%A7%88%EA%B3%A0-%EA%B4%80%EB%A6%AC%EC%8B%9C%EC%8A%A4%ED%85%9C?node-id=14-1509)
- 구성: GONE 로고, 소개 문구, 아이디/전화번호 입력 필드, 비밀번호 입력 필드, 회원가입 링크, 로그인 CTA
- 디자인 기준: 좌우 24pt 여백, 입력 필드 하단선, CTA 높이 54pt·모서리 반경 16pt, 최소 터치 영역 44pt를 유지합니다.
- 디자인 시스템: 기존 `doc/DESIGN_SYSTEM.md`의 semantic color 및 `Button`, `TextField` 상태 정의를 먼저 적용합니다. 로그인 화면에 필요한 토큰·컴포넌트만 최소 범위로 구현합니다.

### 상태

- 초기: 두 필드는 비어 있고 로그인 CTA는 비활성화합니다.
- 입력: 필수 입력값이 충족되면 CTA를 활성화합니다. 세부 형식 검증 기준은 API 명세 확인 후 확정합니다.
- 진행: 중복 요청을 막고 CTA에 로딩 상태를 표시합니다.
- 인증 실패: 아이디/전화번호 또는 비밀번호 오류를 사용자가 이해할 수 있는 문구로 표시합니다.
- 네트워크/서버 오류: 재시도할 수 있는 오류 안내를 표시합니다.
- 성공: 인증 정보 저장 후 인증 완료 목적지로 전환합니다. 목적지는 앱 진입 구조(스플래시 포함) 설계 시 확정합니다.

### 접근성

- 입력 필드에는 역할과 현재 오류를 VoiceOver가 읽을 수 있는 레이블·힌트를 제공합니다.
- 비밀번호는 보안 입력으로 처리하고 표시/숨김 제어가 디자인에 추가되면 별도 접근성 레이블을 제공합니다.
- Dynamic Type으로 텍스트가 커져도 내용이 잘리지 않도록 세로 스크롤과 레이아웃 여유를 둡니다.
- 오류는 색상만으로 전달하지 않고 텍스트로 함께 전달합니다.

## 4. 데이터 및 아키텍처

### 데이터 흐름

이번 기능은 **MVVM을 기본 구조**로 사용합니다. 로그인 API·Keychain처럼 외부 I/O가 연결되는 시점에만 UseCase와 Repository를 추가해, 화면 규모에 비해 과도한 계층 분리를 피합니다.

```text
LoginView
→ LoginViewModel
→ LoginUseCase
→ AuthRepository (protocol)
→ RemoteAuthRepository / APIClient
→ 인증 API
```

- `LoginView`: 입력·버튼·상태 UI 표현과 사용자 이벤트 전달만 담당합니다.
- `LoginViewModel`: 입력 상태, 유효성, 로딩, 사용자 노출 오류와 화면 이동 이벤트를 관리합니다.
- `LoginUseCase`: 로그인 실행 및 세션 저장 정책을 담당합니다.
- `AuthRepository`: 인증 데이터 접근을 추상화합니다.
- `RemoteAuthRepository`: API 요청·응답 변환과 오류 매핑을 담당합니다.
- `SessionStore`: 인증 토큰은 UserDefaults가 아닌 Keychain에 저장합니다.
- 테스트: `AuthRepository`를 mock으로 주입해 ViewModel/UseCase의 성공·실패·로딩 상태를 검증합니다.

### 외부 의존성 및 결정 필요 항목

제공된 Notion API 명세서와 참고 페이지는 현재 연결된 Notion 권한에서 조회되지 않았습니다(페이지 접근 불가). 따라서 아래 항목은 추정 구현하지 않고, 접근 권한 또는 명세 공유 후 이슈 본문과 구현 계획에 반영합니다.

- 로그인 endpoint·HTTP method·base URL
- 요청 필드명과 아이디/전화번호 허용 규칙
- 성공 응답의 access token / refresh token / 사용자 정보 구조
- 토큰 만료·재발급 방식 및 로그아웃 시 폐기 정책
- 인증 실패, 계정 상태, 네트워크 오류의 응답 코드·메시지 매핑
- 로그인 성공 후 최초 목적지 및 회원가입 화면 전환 방식

- [x] ViewModel 단위 테스트와 기기·시뮬레이터 QA를 수행하고 결과를 이슈 보고서에 기록한다.

## 6. 완료 기준

- [ ] 피그마 로그인 화면의 정보 계층과 주요 여백·색상·CTA 상태가 iOS 환경에서 일관되게 구현된다.
- [ ] 아이디/전화번호와 비밀번호가 모두 입력되기 전에는 로그인 CTA가 비활성화된다.
- [ ] 로그인 요청 중 중복 제출이 방지되고 로딩 상태가 표시된다.
- [ ] 인증 성공 시 명세에 맞는 세션을 Keychain에 저장하고 다음 화면 전환 이벤트를 전달한다.
- [ ] 인증 실패·네트워크 오류·서버 오류가 명세에 따른 사용자 안내와 재시도 수단을 제공한다.
- [ ] VoiceOver, Dynamic Type, 44pt 이상 터치 영역을 확인한다.
- [ ] 성공·실패·로딩 상태에 대한 단위 테스트와 QA 결과가 기록된다.

## 7. 특이 사항 / 기술 검토

- API 계약이 확인되기 전에는 endpoint, DTO, 토큰 정책을 임의로 구현하지 않습니다.
- 로그인 기능의 PR base는 반드시 `dev`입니다. `main` 대상 PR은 전체 개발과 통합 QA가 완료되고 개발자가 명시적으로 요청한 최종 릴리즈에만 생성합니다.
- 이번 계획 승인 후에만 GitHub 이슈를 작성하고, `dev`에서 `feat/<이슈번호>-로그인` 브랜치를 분기합니다.
- 구현 중 API 계약 또는 화면 요구사항이 달라지면 계획서를 먼저 갱신하고 재검토를 받습니다.
