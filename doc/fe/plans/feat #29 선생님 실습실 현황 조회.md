## 1. 목적 및 배경

선생님은 실습실을 직접 예약하는 사용자가 아니라 학생들의 실습실 신청 현황을 확인하고 승인 판단에 필요한 정보를 조회하는 사용자다. 기존 선생님 실습실 탭의 학생 예약 흐름을 역할별 현황 조회 화면으로 전환한다.

## 2. 사용자 시나리오

```text
선생님이 실습실 탭에 진입한다
→ 날짜와 층을 선택한다
→ 실습실별 예약/미예약 카드와 야자시간·방과후 등 이용 시간 태그를 확인한다
→ 예약된 카드를 누른다
→ 실습실명, 이용일, 이용시간, 신청자, 인원, 목적, 위치를 상세 페이지에서 확인한다
→ 뒤로 가기로 현황 목록으로 돌아온다
```

## 3. 화면 및 UX

### 화면 구성

- 선생님 목록: `실습실 대여`, 날짜, 층 선택, 층별 실습실 카드 목록
- 카드: 순번, 실습실명, 신청자/인원, 사용 목적 요약, 이용 시간 태그, 미예약 상태
- 상세: 실습실명, 이용 시간 태그, 날짜, 과목/실습실명, 이용시간, 대여자, 사용 목적, 사용 위치
- 학생 화면: 기존 실습실 예약 UI 유지

### 상태

- 정상 / 로딩 / 빈 상태 / 오류 상태
- 미예약 카드는 상세 이동이 불가능하며 `미예약` 상태를 표시한다.
- 예약 카드만 탭 가능하고, 상세 화면에는 뒤로 가기 동작을 제공한다.

### 접근성

- 카드 전체를 하나의 버튼으로 읽고 실습실명·예약자·이용시간·상태를 함께 제공한다.
- 층 선택과 날짜 선택에 명확한 레이블을 제공한다.
- 태그 색상만으로 이용 시간을 구분하지 않고 텍스트를 함께 표시한다.
- 카드와 뒤로 가기 버튼은 최소 44pt 터치 영역을 보장한다.

## 4. 데이터 및 아키텍처

### 데이터 흐름

- API / Repository: 기존 `LabReservationRepository`를 확장하거나 교사용 `TeacherLabRepository`를 추가한다.
- UseCase: 선생님 현황 조회와 상세 표시 데이터를 분리한다.
- ViewModel 상태: 선택 층·날짜, 목록 로딩/성공/실패, 선택된 예약 상세를 관리한다.
- Model: 실습실, 예약 상태, 이용 시간 타입(야자시간·방과후 등), 신청자·인원·목적·위치를 표현한다.
- 역할 분기: `AppTabView`에서 선생님은 현황 조회 ViewModel을 주입하고 학생은 기존 예약 ViewModel을 사용한다.

### 외부 의존성 및 결정 필요 항목

- 실제 승인/예약 API는 확정되지 않았으므로 Mock Repository로 UI와 데이터 흐름을 구현한다.
- 이번 범위에서는 승인/반려 액션을 추가하지 않고 조회에 집중한다.
- 최신 `dev`에 반영된 선생님 상벌점 탭 분기를 유지하고, `AppTab.points` 누락 여부를 함께 빌드 기준으로 보정한다.

## 7. 기술 검토

- 기존 학생 예약 기능을 역할 조건문으로 과도하게 분기하지 않고, 교사용 현황 화면을 별도 Presentation 계층으로 두어 책임을 분리한다.
- Mock 데이터는 최소 2개의 예약 카드(야자시간·방과후)와 미예약 카드를 포함한다.
- 상세 화면의 날짜·위치·목적 데이터는 Model에서 제공하고 View는 표시만 담당한다.
